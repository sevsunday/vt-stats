# AGENTS.md

## Project

VT Stats — static-site dashboard for Battlezone: Combat Commander match statistics. Python pipeline processes raw protobuf session data into pre-computed JSON; static HTML/JS/CSS dashboard renders it.

## Before Making Any Change

1. Read the relevant rule file(s) from `.cursor/rules/`
2. Follow `DEVELOPER_GUIDE.md` for schema and architecture details
3. Never skip these — they prevent regressions and ensure consistency

## Rule Files

- `scripts/elo_commander.py` — pipeline-side **VTSR-C** (Commander Rating, v2 — **experimental**; econ composite inert). Pure module (no I/O) mirroring the `elo.py` contract; `compute_commander_elo(all_match_data, elo_history)` returns `(elo_commander_current, elo_commander_history)` dicts, written by `scripts/process_stats.py` immediately after the canonical VTSR-T emit to `data/processed/elo_commander_current.json` + `elo_commander_history.json` (own `schema_version: 2`; both in the `load_cache_index()` skip set — critical). **Outcome-pure (`α_c = 1`) win/loss ELO between the two commanders of every DETERMINED rated match** — present in canonical `elo_history` with deltas (inherits the ≥6-player / ≥240s / non-cancelled gates), `winner.team ∈ {1,2}` via `decided_by ∈ DETERMINED_DECIDED_BY = (adjudicated, attested, clean_win, contested)`, both commanders identified from `leaderboard[].is_commander` (fallback `team_leaders`); attested/adjudicated draws score S = 0.5 both sides. **Team-strength handicap** in the expected score: `E_A = 1/(1+10^(−((R_A−R_B)+λ(T_A−T_B))/400))`, `T` = mean pre-match VTSR-T of each team's non-commander rated rows from the elo_history deltas' `before` values (zero leakage; either side with no thug rows → term 0), `λ = CMDR_LAMBDA_TEAM_HANDICAP = 1.0` (validator-ablated over {0, 0.5, 1.0, 1.5}). Classic chess constants (deliberately different from VTSR-T's performance regime): logistic scale **400**, **symmetric K** `40 → 20` decaying over the first `CMDR_PROVISIONAL_PRIOR = 5.0` duels, **no rating floor**, anchor 1500, provisional badge below `CMDR_PROVISIONAL_THRESHOLD = 5` rated games. **v2 (proto v4 overhaul): five-axis economy composite, structurally INERT at `CMDR_ALPHA_C = 1.0`** — axes `pool_tempo` / `production_output` / `thug_supply` / `econ_efficiency` / `upgrade_investment` from the v4 `economy`+`builds` blocks (constructor-free by design), **within-match differential normalization** `z = clip(d / shrunk_std(axis), ±2)/2` (rolling team-1-perspective RMS, seed prior + `CMDR_ECON_STD_SHRINKAGE = 10` pseudo-duels, snapshot-before-duel/update-after), `P₁ = Σw·z/Σw` (`COMMANDER_ECON_WEIGHTS` .30/.25/.20/.15/.10), `P₂ = −P₁`; blend `S' = α_c·S + (1−α_c)·(P+1)/2` on telemetry duels only (both v4 flags), **code branches on `α_c < 1.0`** so the inert path never touches blend arithmetic (golden gate `_investigation/golden_vtsrc_v2.py` — every duel byte-identical to v1); fallback duels score outcome-pure at ANY α_c (ratified policy); W/L/D records tally RAW outcomes; formulas + seed priors + promote rule FROZEN in `critique/decisions/vtsr-c-v2-composite.md` (flip below 1.0 only at ≥25 telemetry duels AND ≥3 axes sign-agreement >0.55 with none <0.35 AND ablation improves-or-holds accuracy while improving log-loss; axis discard <0.40 at n≥40). New fields: per-duel `performance {available, p, axes{axis:{diff,std,z}}}` + per-side `score_blend {alpha_c, s_raw, s_blended}`; per-rating `duels_with_telemetry`; top-level `alpha_c`/`econ_weights`/`econ_std_prior`/`econ_std_shrinkage`/`thug_supply_cap`/`econ_std_observed`. History `duels[]` carry full audit blocks (`commanders.{1,2}.{before,after,delta,expected,k,score}` — expected pair sums to 1 — + `team_handicap.{t1_thug_mean,t2_thug_mean,diff,lambda}`). **Corpus-wide, picker-unaware, NOT in the pipeline cache key; the dashboard thug-only toggle does NOT apply (separate ladder). No `PIPELINE_VERSION` / `ELO_SCHEMA_VERSION` / `match.schema_version` interaction** (recomputes every run). Consumers (all 404-safe): ELO page ladder card (`#section-vtsr-c` + `renderCommanderLadder()` in `js/elo.js` — v2 adds chevron-expandable per-row detail panels with duel log + latest econ-telemetry axis bars + `v4×N` telemetry chips; `elo_commander_history.json` now fetched at ELO-page boot) + all four explainer pills (`commanderLadderHtml()` in `js/vtsr-explainers.js` + the "Economy is recorded, not yet scored" fairness card + Does-it-work econ-axis funnel + α_c ablation table from `latest_detail.vtsr_c_perf`), dashboard Commander Cohort top-5 strip (`ensureCommanderEloLoaded()` + `_cohortVtsrCStripHtml()` in `js/app.js`), player-page **Commander Rivalries** panel (`js/player.js` — headline strip / top opponent / top-5 enemies / nemesis-best chips + **VTSR-C rating time-series chart** (`ensureCmdrEloHistoryLoaded()` + `drawCmdrRatingChart()`) + **career commander-economy stat block** (`renderCmdrEconBlockHtml()` from the aggregator's v17 econ fields); per-opponent tallies computed client-side from the contributions walk since the aggregator's `head_to_head` caps at top-10 globally). Algorithm spec: `DEVELOPER_GUIDE.md` §13.12. Output schemas: `docs/DATA_DICTIONARY.md` §11.

## Key Conventions

- `scripts/statsgate.proto` is the single source of truth for the **current (v4)** raw data schema. All docs, rules, and pipeline code must match it. When it changes, regenerate `scripts/statsgate_pb2.py` and `vendor/protobufjs/statsgate.proto.json`; everything downstream updates.
- **Triple-descriptor decode (v1/v2/v3/v4 corpus split).** The pipeline transparently supports the legacy schema (`scripts/statsgate_v1.proto`, separate `DamageDealt`+`DamageReceived` events), the frozen v2 schema (`scripts/statsgate_v2.proto`, unified `DamageDealt` + `Race` enum + `shutdown_requested` + `BulletHit.distance_to_target` + header identity maps), the v3 schema (identity maps `reserved` → per-tick `players` PlayerInfo roster; host-attested `game_outcome`), and the current **v4** schema (**purely additive over v3 — no v3 freeze**: per-team `ResourceState` on every `UpdateTick` + the `BuildEvent` oneof arm 9). `load_session()` returns `(session, schema)` where `schema` is `"v1"` / `"v2"` / `"v3"` / `"v4"` — **v4 is detected by presence of any `build_event` arm or resource-bearing `update_tick`, checked BEFORE the `header.players` branch** (a degenerate v4 file with an empty roster must not fall through to the frozen-v2 re-parse, which would silently drop its telemetry); then **v3 by `header.players` presence (v2-vs-v3-vs-v4 have no wire conflicts, so parse success proves nothing)**, then the legacy v2/v1 dance runs on the frozen v2 descriptor. The consumer loop normalizes damage paths to a single `DamageEvent` shape and `_build_identity_maps()` normalizes identity (v3+: Steam64 validity gate against empty-slot garbage + **evidence-first slot placement** — active players sit at the majority-vote slot from the engine's per-event `team` attributions because `PlayerInfo.teamnum` is only the first-seen slot and lobby shuffles corrupt it silently; no-evidence spectators keep/overflow-within their hinted side by presence, `ROSTER_OVERFLOW_MIN_SHARE = 0.25`; all resolutions audited on `match.roster_conflicts`) so downstream aggregators are schema-agnostic. The detected schema is stamped on `match.proto_schema_version` (debugging telemetry only — UI never branches on it). The same v4-presence / v3-presence / v2-fallback / v1-catch dance happens in the Raw Data Browser. Maintain byte-for-byte parity for the v1/v2/v3 corpus on any schema-related change — the only allowed diffs are version bumps and new optional fields.
- **Build ledger: charge-at-START + bulk cancel (match.schema_version 20, PIPELINE_VERSION 35).** The ledger assumed scrap is deducted at QUEUE; the engine charges each unit when **IT STARTS building** (isolated queues coincide, which is why the original 92-96% audit couldn't separate them). Display-only; gate `_investigation/golden_builds_inert.py` perturbs every affected field and requires byte-identical VTSR-T + VTSR-C, deliberately sparing `scrap_spent_units` / `ships_built` (VTSR-C's econ composite reads those and this change doesn't touch them). **Producer model**: recycler / factory / armory are one-per-team (a faction factory upgrade REPLACES its predecessor), each holds ONE order at a time, stackable N-deep with the same ODF. **A bulk cancel clears the ENTIRE queue** and fires one CANCEL per queued unit, but only the in-production unit was ever charged — so a burst books ONE unit into `outflow_cancelled_cost` + `cancel_sunk_cost`, enqueues ONE refund expectation, frees the rest, and resets the lane queue. Verified: burst size == tracked depth on every clean case (Harvesters 3=3/2=2/1=1, artillery 3=3, other side 4=4, armory 1=1); a 3-Harvester stack cancel returned ~10 scrap not 30; production is strictly sequential (5 Harvesters exactly 200 ticks apart, then 7 pods exactly 71 ticks apart); only 205 of 784 pod QUEUE ticks show the charge at queue. **Two-level bookkeeping — do NOT re-key the per-stem FIFO to lane**: the per-`(side, stem)` FIFO matches events to orders (BUILD/CANCEL carry the ODF, so a Harvester build must retire a Harvester order) while a new per-`(side, lane)` `build_lane_queue` tracks what is in production; blind head-popping mis-attributes once tracking drifts (~18 scrap on the reference match). **Collector gap**: bulk-cancel emission is **capped at 10 CANCEL events** — every depth>burst case has burst == exactly 10, all pure Service Pod queues (pods are the only orders exceeding the engine's 10-slot queue; no non-pod queue passes 7, pod depth hit 39). So **`orders_trimmed` comes from the tracked depth, NEVER the burst size**; the shortfall is `cancel_events_truncated` (54). Resetting the queue per burst self-heals the otherwise-monotone offset — do not mistake it for a standing backlog. **Unmatched cancels still charge one unit** (the QUEUE was dropped, not the CANCEL invented; all 5 corpus-wide are armory, one ODF has 2 cancels and 0 queues) → `cancels_unmatched`. `outflow_pending_at_end_cost` becomes the **in-progress head unit per lane** (186 → 20). New `economy.teams{n}.outflow_clamped_cost` = scrap destroyed when a dying pool drops `max_scrap` below the bank (20 / 54). **The outflow ledger is now a strict PARTITION** — the six components plus `scrap_outflow_unaccounted` sum to `scrap_outflow_gross` exactly, gated; residual moved **-552 → +24** and **-72 → -64**, the remainder being the deliberately-untouched inferred-mode constructor lane (zero cancels, zero BUILD events, multiple constructors possible so one-order-per-producer fails there). New `builds.teams{n}` fields `orders_backed_out` / `orders_trimmed` / `cancels_unmatched` / `cancel_events_truncated` / `orders_open_at_end`; `units_cancelled` stays the RAW event count for tier-2 reconcile and must never be displayed as "cancelled orders". Card: `Cancelled orders` replaced by `Orders backed out` (real sunk cost) + `Queue trimmed` (explicitly free), both self-omitting at zero.
- **Income classifier + human-only thug losses (match.schema_version 19, PIPELINE_VERSION 34).** Three measured, display-only corrections on the Economy tab; gate: `_investigation/golden_income_thug_inert.py` **perturbs** every income / `thug_supply` value (2090 fields) and requires byte-identical VTSR-T + VTSR-C (value-insensitivity, which a value correction needs — the v18 gate only strips fields). ## When Schema Changes

1. If the new schema removes/reshapes fields the existing corpus depends on, FIRST freeze the outgoing schema (`statsgate_vN.proto` with package renamed to `statsgate_vN` + pb2 + protobufjs JSON — the v2/v3 precedent), then replace `scripts/statsgate.proto` with the new version
2. Follow `.cursor/rules/schema-migration.mdc` checklist
3. Update pipeline, JSON output, JS rendering, `data-schema.mdc`, and `DEVELOPER_GUIDE.md` — in that order
4. Regenerate the raw-browser descriptor: `npx -y -p protobufjs-cli pbjs -t json scripts/statsgate.proto > vendor/protobufjs/statsgate.proto.json` (invoke `protobufjs-cli` explicitly; on PowerShell run the redirect through `cmd /c` to avoid UTF-16 output)
5. Verify the Node/browser decode path still matches the Python pipeline by running `scripts/verify_proto_decode.mjs` on one file per schema era (see the script header for setup) before shipping the new schema
